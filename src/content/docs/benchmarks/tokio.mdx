This benchmark compares Rust’s Tokio with Knitting `0.1.77` on Bun, Node.js
and Deno. Each test sends a value to one worker and receives it back.

The result changes with payload size: Tokio leads for 1–16 KiB and 1 MiB
binary payloads, while Knitting on Bun and Node.js is slightly ahead at
32–512 KiB. The charts show average time per batch; lower is better.

Benchmark source: [`mimiMonads/knitting-vs-tokio-bench`](https://github.com/mimiMonads/knitting-vs-tokio-bench).

## What this benchmark measures

Each batch waits for every reply. The tests cover:

- `f64` values
- `1 MiB` strings
- `Uint8Array` values from `8 B` to `1 MiB`
- a separate `Arc<Vec<u8>>` sweep for small shared-byte payloads

The machine is an AMD Ryzen 7 4700U running Ubuntu 23.10 x86_64. Every runtime
uses the same batch sizes (`1`, `10`, and `100`), warm-up, measured iterations
and percentile reporting.

The report names source files but omits Rust, Tokio and JavaScript runtime versions.

## Small payloads: `f64`

For an 8-byte number, the fastest runtime depends on batch size:

- With one call, Node.js is fastest at `6.63 µs`, followed by Bun, Tokio and Deno.
- With 10 calls, Deno is fastest at `11.97 µs`, compared with Tokio’s `27.50 µs`.
- With 100 calls, Node.js is fastest at `62.33 µs`; Deno and Bun also finish ahead of Tokio.

For p99 batch time, Tokio leads at `n=1` and Bun leads at `n=10` and `n=100`.

## Large payloads: `1 MiB`

At `1 MiB`, Tokio leads most comparisons:

- Tokio is fastest for the large-string test at `n=1` and `n=100`. Bun is just ahead at `n=10`.
- Tokio leads the `Uint8Array` test at every batch size: `272.81 µs`, `4.64 ms`, and `37.83 ms`.

These timings include copying the payload on both the request and the reply.

## How the payload size changes things

This sweep keeps the batch at `100` and grows a binary payload from `8 B` to `1 MiB`.

Bun is fastest from `8 B` through `512 B`. Tokio takes the lead from `1 KiB` through `16 KiB`, then Bun and Node.js move slightly ahead through `512 KiB`. At `1 MiB`, Tokio is fastest again at `29.48 ms`.

## A separate shared-ownership reference

Tokio uses `Arc<Vec<u8>>` here: sending a value increments a reference count
instead of copying bytes. This measures shared ownership separately from the
copying tests above.

At `8 B` through `256 B`, Bun is still faster than the Tokio `Arc` path. At `512 B`, the two are close: `74.78 µs` for Bun versus `79.51 µs` for Tokio.

## What each side does

Both implementations:

- Prepare inputs before timing.
- Use one worker thread and wait for the whole batch.
- Copy strings and bytes on both send and reply.

Tokio allocates and copies `String` and `Vec<u8>` with `clone()`. Knitting
copies into preallocated shared memory. The timings include those costs.

## Why the results change with payload size

Knitting keeps transport data in reused typed-array-backed buffers. Small primitive values fit in the per-call header, while larger values spill into a preallocated shared payload buffer. Fixed worker lanes and a small allocation bookkeeping layer reduce general-purpose allocation in the hot path.
