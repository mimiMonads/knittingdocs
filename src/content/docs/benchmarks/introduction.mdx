- [HTTP latency](#http-latency): one worker reduced `/ping` p99 by {hono.reductions[0]}%

## HTTP latency

In a Hono server, `/ssr` renders React, `/jwt` signs a token, and `/ping`
returns a small JSON object. Moving `/ssr` and `/jwt` to one worker leaves
`/ping` on the main thread, where it no longer waits behind that CPU work.
Both servers received 2,000 requests per second on each route.

**Setup:** Bun 1.4.0, Intel Xeon Platinum 8168, 16 dedicated cores, Ubuntu
24.04. A separate machine generated the load.
[Full report](/documents/hono-16core-benchmark.md).

  caption="p99 response time at 6,000 requests per second in total."
  groups={hono.latencyGroups}

`/ping` p99 fell by {hono.reductions[0]}%, `/ssr` by {hono.reductions[1]}%,
and `/jwt` by {hono.reductions[2]}%. Here, p99 is the response time within
which 99% of requests completed.

Both servers handled all 6,000 requests per second successfully. CPU usage
was similar:

  unit="cores"
  legend={{ baseline: 'Hono only', knitting: 'Hono with one Knitting worker' }}
  caption="CPU used by the server process during the same runs."

The fixed-rate repeat used {repeatCores} cores, close to the 1.08-core baseline.

Under saturating load, the same change raised total throughput from {hono.saturation[0].rps.toLocaleString("en-US")} to
{hono.saturation[1].rps.toLocaleString("en-US")} requests per second, and CPU use
from {hono.saturation[0].cores} to {hono.saturation[1].cores} cores.

## CPU throughput

The task finds primes up to 10,000,000 in chunks of 250,000 and returns them
to the main thread. The main thread processes chunks too: four workers means
five threads doing the search.

**Setup:** Apple M3 Ultra, macOS arm64; Node.js 24.12.0, Deno 2.6.6 and
Bun 1.3.6. Bars show average time to finish the search.

<CompareBars
  unit="ms"
  legend={{ baseline: 'Main thread only', knitting: 'Main thread plus Knitting workers' }}
  caption="Time to finish the whole range on Node.js."
  groups={primeGroups}
/>

With four extra threads the run finished {primeSpeedups.node}× faster on Node.js,
{primeSpeedups.deno}× on Deno and {primeSpeedups.bun}× on Bun. These timings
include sending the results back to the main thread.
The [reports](/benchmarks/results/#runtime-reports) include the other worker counts.

## Typesetting a document

[knit-tex](https://github.com/mimiMonads/knit-tex) typesets a 216-page copy of
*Pride and Prejudice* to PDF. Four workers reduced warm completion time on
both runtimes:

| Runtime | Main thread | Four workers | Speedup |
| --- | ---: | ---: | ---: |
| Node.js 24.19.0 | 427 ms | 229 ms | 1.86× |
| Bun 1.4.0 | 449 ms | 254 ms | 1.77× |

**Setup:** Intel Core i5-1135G7, four physical cores. Each result is the median
of five runs using an already initialized pool. Output hashes matched the
main-thread output on each runtime.

Four workers used more total CPU time. Cold runs and runs that started a new
CLI process were slower than the main thread, so this gain matters when the
pool handles repeated work. See [Results and methodology](/benchmarks/results/#typesetting-a-long-document)
for CPU times, work-stealing results and source reports.

## Binary round trips against Tokio

This test compares copying a binary payload to one worker and back. Tokio
clones a `Vec<u8>` on send and reply; Knitting sends a `Uint8Array` through
preallocated shared memory. Timings include allocation and worker coordination.

**Setup:** AMD Ryzen 7 4700U, Ubuntu 23.10 x86_64. Runtime versions were not
recorded. [Full comparison](/benchmarks/tokio/).

<CompareBars
  unit="ms"
  legend={{ baseline: 'Tokio (Rust)', knitting: 'Knitting' }}
  caption="Time for 100 round trips of a 256 KiB payload."
  groups={copyGroups}
/>

From 32 KiB to 512 KiB, Knitting on Bun and Node.js took {copyRange.fastest}% to
{copyRange.slowest}% less time than Tokio. On Deno it ranged from
{copyRange.denoLess}% less to {copyRange.denoMore}% more.

From 1 KiB to 16 KiB, Tokio was up to {smallCopyLead}× faster. At 1 MiB it was
{largeCopyLead} faster. The [Tokio page](/benchmarks/tokio/#how-the-payload-size-changes-things)
has every size and explains how copying differs from its separate shared-ownership test.

## Reproduce

| Test | Harness |
| --- | --- |
| HTTP latency | [Hono report](/documents/hono-16core-benchmark.md): server in Appendix B, harness in Appendix C. |
| Worker calls | `bench/latency.ts` in [`mimiMonads/knitting`](https://github.com/mimiMonads/knitting); run `./run.sh` from the repository root. |
| CPU throughput | `bench/withload.ts` in the same repository; run `./run.sh`. |
| Tokio comparison | The `latency` suite in [`mimiMonads/knitting-vs-tokio-bench`](https://github.com/mimiMonads/knitting-vs-tokio-bench): `node scripts/bench.mjs latency`. |

Use Knitting `0.1.77` to match the tested release. Measure on your target
hardware: payload size, runtime and worker count affect the result.
