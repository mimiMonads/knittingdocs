This example parses JSON input, normalizes user data, and renders a React
component to an HTML string in a worker using `renderToString`.

## How it works

The host generates JSON payload strings. The host path calls `renderUserCardHost`
directly; the worker path sends the same payloads through `createPool`. The
benchmark checks that the total output lengths match before timing both paths
with `mitata`.

Three files:

- `bench_react_ssr.ts` -- the benchmark itself
- `render_user_card.tsx` -- the SSR component and worker task
- `utils.ts` -- input payloads and normalization helpers

## Deno setup (TSX + npm)

If you run this with Deno and see `Uncaught SyntaxError: Unexpected token '<'`, set a root `deno.json` so Deno transpiles TSX and resolves npm packages:

```json
{
  "nodeModulesDir": "auto",
  "compilerOptions": {
    "jsx": "react-jsx",
    "jsxImportSource": "react"
  }
}
```

on your component, payloads, available cores, and other work on the host.

:::note
The check compares total output lengths. It can detect a size mismatch, but
equal lengths do not prove that the HTML content is identical.

## Sizing the pool

Four workers without an inliner were roughly `1.8–1.9×` faster than the host
in this batch test, with about two thirds less allocation per iteration.
One worker plus an inliner was slower: it paid transport costs while the
inliner kept rendering on the host.

Start with 2–4 workers and measure your component and payloads. Add the inliner
only if it improves the result.

## Keeping rendering off the request thread

`renderToString` is synchronous and CPU-bound -- it walks your component tree and builds an HTML string. For an individual request, it may be fast, but under load it blocks the event loop and everything else waits. Moving SSR to a worker pool means your main thread stays free to accept requests and handle I/O while rendering happens in parallel. The Hono server example shows what this looks like in a real HTTP server context.
